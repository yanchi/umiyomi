# Research: 緯度・経度の入力サポート

**Feature**: 003-coordinate-input-support | **Date**: 2026-10-05

Technical Context に NEEDS CLARIFICATION は残っていない。以下は、仕様を実装に落とすときに判断が必要だった点の決定事項。
前提として 001（`GET /` と `GET /forecast?lat=..&lon=..`、`CoordinateQueryParser`）と 002（お気に入り、`node --test`）が実装済み。

---

## R1. 表記の読み取りをどの層に置くか

**Decision**: 座標の表記（十進数・度分・度分秒・1 行の「緯度, 経度」・方角の文字・全角）の読み取りは、既存の `CoordinateQueryParser` と同じ
`Presentation/Web/Input` に置く。1 欄の文字列を読む `CoordinateNotationParser` と、2 欄の組み合わせ（FR-004）・順序の誤り（FR-022）を判定する
既存の `CoordinateQueryParser` に分ける。読み取りの結果は従来どおり丸め済みの `float` として `ViewMarineForecastInput` に渡す。
Domain（`Coordinate`）・Application（UseCase・DTO）は変更しない。

**Rationale**:
- 表記はフォームに入力された文字列の形式の問題で、地点の意味（範囲・同一地点の判定）は従来どおり Domain の `Coordinate` が持つ。
  Domain を変えないので、Domain 設計のレビュー対象を増やさない
- Deptrac の規則上、Presentation は Domain を参照できない。読み取りを Domain に置くと、UseCase の入力を文字列に変える必要があり、
  アプリ化のときに JSON API が数値で受け取る場合と食い違う
- 読み取りはサーバーだけで行う（spec Assumptions）。ブラウザ側に同じ規則を持たないので、規則の置き場所は PHP の 1 か所になる

**Alternatives considered**:
- Domain に `CoordinateNotation` を置き、UseCase に文字列を渡す：上記のとおり UseCase の入力が Web の入力形式に引きずられる
- Symfony Form + カスタム DataTransformer：2 欄の相互依存（FR-004）を Form の仕組みで書くと、専用パーサーより読みにくい（001 research R7 と同じ判断）

アプリ化で同じ表記をサーバーで読む必要が出たら、そのとき Application 層へ移す（パーサーは Symfony に依存しない素の PHP クラスにしておく）。

## R2. FR-023 の「十進数として正確に計算して四捨五入」を bcmath なしで実現する

**Decision**: 浮動小数点で計算せず、数字の文字列から「小数点以下 2 桁に丸めた値 × 100」の整数（以下 hundredths）を直接求める。
正の大きさで計算し、最後に符号を付ける（＝0 から遠い方向への四捨五入）。必要な桁は次のとおりで、どの表記も入力の桁数に関係なく PHP の `int` で正確に求まる。

| 表記 | hundredths の求め方 | 必要な桁 |
|---|---|---|
| 十進数 `D.f1f2f3…` | `100·D + f1f2 + (f3 ≥ 5 ? 1 : 0)` | 小数点以下 3 桁目まで |
| 度分 `D°Mi.m1…'` | `100·D + floor((10·Mi + m1 + 3) / 6)` | 分の整数部と小数点以下 1 桁目 |
| 度分秒 `D°Mi'Si.s1…"` | `100·D + floor((120·Mi + 2·Si + 36 + (s1 ≥ 5 ? 1 : 0)) / 72)` | 秒の整数部と小数点以下 1 桁目 |

度分の式の根拠：`D + m/60` を 100 倍すると `100·D + 5m/3`。四捨五入は `floor(5m/3 + 1/2) = floor((10m + 3) / 6)`。
`10m = 10·Mi + m1 + r`（0 ≤ r < 1）で、整数 K と 0 ≤ r < 1 に対して `floor((K + r) / 6) = floor(K / 6)` なので、m1 より下の桁は結果に影響しない。
度分秒も同じ考え方で `100·D + (60·Mi + s) / 36` の四捨五入を `floor((120·Mi + 2s + 36) / 72)` とし、`2s` の小数部の繰り上がりだけを s1 で判定する。

例：`27°45.3'`（= 27.755）→ `2700 + floor(456 / 6) = 2776` → 27.76。`27°45'18"`（= 27.755）→ `2700 + floor(5472 / 72) = 2776` → 27.76。
`S27°45.3'` → -27.76。十進数の `27.755` → 27.76、`27.7549999999999999` → 27.75（float に変換すると 27.755 になり誤って 27.76 になる例）。

範囲の検証（FR-009、001 の「丸める前の値で検証」）も丸める前の正確な値で行う：
- 十進数：整数部が上限未満なら範囲内、上限と等しければ小数部がすべて 0 のときだけ範囲内
- 度分・度分秒：度が上限未満なら範囲内（分・秒 < 60 なので D + 1 未満）、上限と等しければ分・秒の数字がすべて 0 のときだけ範囲内

hundredths を `float` にするときは `hundredths / 100` とする（IEEE の除算は正しく丸められ、`Coordinate` の `round($x, 2)` を通しても値が変わらない）。

**Rationale**:
- 開発用・本番用イメージに bcmath は入っていない。四捨五入に必要な桁が上の表のとおり有限なので、拡張を足さずに正確に計算できる
- 001 の十進数入力も `(float)` 変換をやめて同じ方法にする（spec Assumptions：FR-023 は 001 にも適用する）
- `Coordinate` の丸め（`round()`）は残す。Presentation から来る値はすでに 2 桁なので実質的に何もしないが、Domain の不変条件として保つ

**Alternatives considered**:
- bcmath（PHP 8.4 の `BcMath\Number`）を両方の Dockerfile に追加：正確だが、拡張の追加と本番イメージの変更が要る。上の方法で足りる
- `(float)` に変換して `round()`：PHP の `round()` は一般的な値では期待どおりだが、桁の多い入力（例：`27.7549999999999999`）で FR-023 と食い違う。SC-002 の「100% 一致」を保証できない

## R3. 文字の正規化

**Decision**: 読み取りの前に、次の対応表で文字を置き換える（`strtr`。Unicode の NFKC は使わない）。

| 置き換え先 | 置き換える文字 |
|---|---|
| 半角数字 `0-9` | 全角数字 `０-９` |
| `.` | `．` |
| `,`（区切り） | `，` `、` `､` |
| `-` | `－` `−`（U+2212） `‐`（U+2010） `‑`（U+2011） `–`（U+2013） |
| `+` | `＋` |
| `(` `)` | `（` `）` |
| 空白 | 全角空白（U+3000）、タブ、改行 |
| `°`（度） | `°` `˚` `º` `度` `d` `D` |
| `'`（分） | `'` `′` `’` `‘` `＇` `分` |
| `"`（秒） | `"` `″` `”` `“` `＂` `秒`、および分の記号 2 つ（`''` `′′` など） |
| `N` `S` `E` `W` | `北緯` `南緯` `東経` `西経`、小文字 `n s e w`、全角 `Ｎ Ｓ Ｅ Ｗ ｎ ｓ ｅ ｗ` |

**Rationale**:
- iPhone のキーボードは既定で「スマート句読点」が有効で、`'` `"` を `’` `”` に置き換える。これを受け付けないと、スマホで度分を手入力した利用者の多くが失敗する（FR-020）
- `º`（序数標識）は度の記号と見た目が近く、一部のキーボード・コピー元で混入する
- NFKC は `″` を `′′` に分解する一方で `′` `’` `、` を変えないなど、結果が直感的でない。対応表にすると、受け付ける文字をテストで列挙できる
- 方角の小文字を受け付ける：従来は指数表記の `e` と区別するために大文字だけを方位と見ていたが、指数表記はもともと受け付けていない

**Alternatives considered**:
- `Normalizer::normalize(NFKC)`（intl）＋追加の対応表：置き換えの規則が 2 段になり、何が受け付けられるかが読み取りにくい

## R4. 1 欄の文字列の文法

**Decision**: 正規化・前後の空白の除去・全体を囲む括弧 1 組の除去のあと、1 欄の文字列を「値 1 つ」か「値 2 つ（1 行の緯度・経度）」として読む。
文法の詳細は [data-model.md](data-model.md) の「受け付ける表記」に定める。要点は次のとおり。

- 値 1 つ＝`[方角] [符号] 本体 [方角]`。本体は十進数（度の記号は付けても付けなくてもよい）・度分・度分秒・ハイフン区切り（方角の文字が必須）
- 度分・度分秒は単位の記号（°・'）で区切りが分かるときだけ。最後の単位の記号（度分の `'`、度分秒の `"`）は省略してよい（例：`27°45.0N`）
- 値 2 つの区切りはカンマ（読点を含む）または空白。3 つ以上は受け付けない（FR-002、spec Edge Cases）
- 1 行の 2 つの値は、**両方に方角の文字があるか、両方にないか**のどちらかに限る。片方だけにある場合は受け付けない
- 度分秒で分に小数がある値（例：`27°45.5'30"`）は受け付けない

**Rationale**:
- 最後の単位の記号の省略：GPS プロッターや漁場の情報で `27°45.0N` のように分の記号を書かない例が多い。度の記号があるので度分と分かる
- 方角の文字の有無をそろえる規則：`N27 45.0`（ハイフンの代わりに空白で書いた度分）を「緯度 27、経度 45」の 1 行と読んでしまうと、
  利用者が意図しない地点の予報を気付かずに見ることになる。両方にそろえる規則にすると、この入力は受け付けずに案内できる。
  地図アプリの出力（`27.75, 129.05`、iPhone の `27.75000° N, 129.05000° E`）はどちらも満たす
- 度分秒の分の小数：正確な丸め（R2）の式が簡単になり、実際の表記にもまず現れない
- 方角の文字が前置か後置かは、文字列の先頭が方角の文字かどうかで決める（`27.75 N 129.05 E` は後置、`N 27.75 E 129.05` は前置）

**Alternatives considered**:
- 空白区切りの数字の個数から度分かどうかを推測する：clarify で「推測しない」と決定済み
- 片方だけ方角の文字がある 1 行を受け付ける：上の取り違えの理由で採らない

## R5. 読み取った地点を URL・入力欄に反映する方法（FR-010）

**Decision**: 入力が有効で、入力欄の文字列が正規形（丸めた値を `%.2f` で書いた文字列。例：`27.75`）でない場合、`GET /forecast` は予報を取得せずに
**303 See Other で正規形の URL へリダイレクト**する。1 行の文字列を使ってもう一方の欄の値を使わなかった場合（FR-004）は、
リダイレクト先に `ignored=lat` または `ignored=lon` を付け、予報画面でそのことを知らせる。

例：`/forecast?lat=27%C2%B045.0%27N&lon=129%C2%B003.0%27E` → `303 Location: /forecast?lat=27.75&lon=129.05`
`/forecast?lat=35.10%2C+139.20&lon=129.05` → `303 Location: /forecast?lat=35.10&lon=139.20&ignored=lon`

入力エラー（422）のときはリダイレクトせず、従来どおり入力した文字列を入力欄に残す（FR-011）。

**Rationale**:
- FR-010 は、入力欄・表示中の地点・URL を十進数で示すことを求めている。JavaScript を使わずに URL を変えるにはリダイレクトしかない
- 正規形の URL では入力欄の値が正規形になり、再読み込み・ブックマーク・お気に入り・FR-021 の「開いたときの文字列」がすべて十進数でそろう
- 予報の取得（回数制限を含む）はリダイレクト先で 1 回だけ行う。リダイレクト元では UseCase を呼ばない
- `27.7500` のような十進数もリダイレクトの対象になる（`27.75` へ）。001 の「正規化した URL へのリダイレクトはしない」を変更する（下記の注意）
- 使わなかった欄の通知をセッション（フラッシュメッセージ）で運ぶと Cookie が必要になる。クエリのほうが状態を持たずに済む

**注意（001 の契約の変更）**: 001 の [web-routes.md](../../001-marine-forecast-view/contracts/web-routes.md) は「入力された文字列はそのまま URL に残る（正規化した URL へのリダイレクトはしない）」としている。
この機能でこれを変更する。画面・URL 設計の変更なので人間のレビュー対象。

**Alternatives considered**:
- リダイレクトせずに 200 で描画し、JavaScript の `history.replaceState` で URL を書き換える：JavaScript が動かない環境で FR-010 を満たせない
- `ignored` を付けたまま再読み込みすると通知が再び出る：文言を「この地点は緯度欄の『緯度, 経度』から読み取りました。経度欄の値は使っていません」とし、
  再読み込み時に出ても誤りにならないようにする。通知を出さない URL（`ignored` なし）はお気に入り・入力欄からの送信で使われる

## R6. エラーメッセージの粒度

**Decision**: 欄ごとに 1 つのメッセージを出す。原因ごとの文言は [contracts/web-ui.md](contracts/web-ui.md) に定める。
読み取れない入力のメッセージには、入力できる表記の例（十進数、「緯度, 経度」、度分、度分秒）を必ず含める（FR-011、US3-1）。
2 欄の組み合わせの誤り（両方に 1 行の文字列）は両方の欄に、1 行の文字列の中身の誤り（範囲外・順序が逆など）はその文字列が入っている欄に出す。

URL（`http://` `https://` で始まる）を貼り付けた場合は、読み取れない入力として扱い、座標をコピーして貼り付けるよう案内する（spec Assumptions）。

**Rationale**: SC-003（案内だけを手がかりに 2 回目までに表示できる）には、原因と直し方の両方が必要。種類を細かく分けすぎず、利用者が直す操作が変わる単位で分ける。

## R7. 入力欄の属性（FR-020）

**Decision**: 入力欄から `inputmode="decimal"` を外し（既定の文字キーボード）、`autocapitalize="off"` `autocorrect="off"` `spellcheck="false"` を付ける。
`type="text"`・`autocomplete="off"` は維持する。

**Rationale**:
- iOS の `inputmode="decimal"` は数字と小数点だけのキーボードになり、カンマ・`°`・方角の文字を打てない（FR-020）
- 自動修正・自動大文字化・スペルチェックは、度分の表記や方角の文字を勝手に書き換える・下線で邪魔をする。スマート句読点（`’` `”`）は R3 で受け付ける
- 十進数を打つときに数字キーボードへ切り替える手間が増えることは、spec Assumptions で受け入れ済み

## R8. 現在地の取得（User Story 4）

**Decision**: ブラウザの Geolocation API（`navigator.geolocation.getCurrentPosition`）を、ボタンを押したときにだけ呼ぶ。

- 表示：「現在地を入力」ボタンを含む領域は `hidden` 付きで出力し、`'geolocation' in navigator` かつ `window.isSecureContext` のときだけ JavaScript が表示する（FR-018、US4-6）
- オプション：`enableHighAccuracy: false`、`maximumAge: 0`。`timeout` オプションには頼らず、**ボタンを押した時点から 15 秒**の独自のタイマーで打ち切る
- 取得中はボタンを `disabled` にし、「現在地を取得しています」を表示する。取得中に押されても重ねて取得しない（FR-017）
- 取得開始時の 2 つの入力欄の値を覚えておき、結果が出た時点でどちらかが変わっていたら上書きしない（FR-017）。そのことを表示する
- 成功したら、緯度・経度をそれぞれ小数点以下 2 桁の文字列にして入力欄に入れる。丸めは `Math.abs(x).toFixed(2)` に符号を付ける
  （`toFixed` は 2 進数の値そのものを最も近い 2 桁に丸めるので、桁の境目の誤差がない。`-0.00` は `0.00` にする）
- 15 秒を過ぎてから届いた結果・エラーは捨てる。拒否（`PERMISSION_DENIED`）とそれ以外（取得不能・時間切れ・非対応）で文言を分ける
- 取得した位置はどこにも送らず、保存しない（FR-015）。サーバーに渡るのは、利用者が送信したときの入力欄の値だけ

**Rationale**:
- 15 秒の起点：spec は「操作から 15 秒以内」。`getCurrentPosition` の `timeout` は許可の確認ダイアログの待ち時間を含まないため、独自のタイマーにする。
  確認ダイアログで 15 秒以上迷った場合は取得できなかった扱いになるが、もう一度押せば取得できる（US4-5）
- `enableHighAccuracy: false`：GPS の測位を待つより速く、2 桁（約 1km）に丸める用途には十分
- `maximumAge: 0`：移動中に古い位置を使わないため
- `isSecureContext`：Geolocation は HTTPS（と localhost）でしか動かない。押しても必ず失敗するボタンを出さない

**Alternatives considered**:
- `navigator.permissions.query` で事前に許可状態を調べてボタンを出し分ける：Safari の対応状況がまちまちで、押したときの結果で案内すれば足りる
- 取得後に自動で送信する：clarify で「入力欄に入れるだけ」と決定済み（FR-014）

## R9. 入力欄が表示中の地点と食い違っていることの表示（FR-021）

**Decision**: 予報画面（予報一覧を表示しているとき）に、`hidden` 付きの案内を入力フォームのすぐ下に出力しておく。
JavaScript が 2 つの入力欄の `value` と `defaultValue`（サーバーが出力した `value` 属性＝画面を開いたときの文字列）を比べ、
どちらかが異なれば表示、両方同じなら隠す。比べるのは `input` イベント、現在地の入力後、`pageshow`（戻る操作でブラウザが入力値を復元した場合）のとき。

**Rationale**:
- 文字列で比べる（clarify で決定済み）。`defaultValue` を使うと、開いたときの値を別に覚えておく必要がない
- 予報一覧がない画面（422・503・429）では、食い違いで誤解する一覧がないので出力しない
- 案内の文言（表示中の地点を含む）は Twig で出力し、JavaScript は表示・非表示を切り替えるだけにする（002 と同じく、文言を Twig に集める）

## R10. JavaScript の構成とテスト

**Decision**: `assets/coordinate-input/` に次の 3 つを置く。

- `position-format.js`：位置（緯度・経度の数値）→ 入力欄に入れる 2 桁の文字列。純粋関数
- `location-request.js`：Geolocation・タイマーを引数で受け取り、1 回の取得（成功・拒否・失敗・時間切れ・取得中）を結果として返す。DOM に依存しない
- `coordinate-input-ui.js`：DOM（ボタン・メッセージ・入力欄・FR-021 の案内）とイベントだけを持つ

前の 2 つを `node --test` でテストする（偽の Geolocation、`node:test` の `mock.timers` で 15 秒を進める）。
DOM の動作はブラウザでの手動確認（quickstart）とする。002 の `no-html-injection.test.js` の対象に `assets/coordinate-input/` を加える。

**Rationale**: 002 と同じ分け方（規則・外部とのやり取り・DOM）。Node.js 20.19（開発用イメージ・CI）は `mock.timers` に対応している。新しいパッケージは追加しない。
