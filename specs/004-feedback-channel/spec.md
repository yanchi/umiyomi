# Feature Specification: フィードバック導線

**Feature Branch**: `004-feedback-channel`
**Created**: 2026-10-05
**Status**: Draft
**Input**: User description: "フィードバック導線"

## Clarifications

### Session 2026-10-05

- Q: フィードバックをどこで受け付けるか？ → A: 運営者が用意する外部のフォームサービスへのリンクとする。UMIYOMI 側でフィードバックを受け取る・保存する・メールで送る仕組みは作らない（FR-001）
- Q: 予報画面から送るとき、地点の緯度・経度と最終更新日時をどう扱うか？ → A: フォームの欄にあらかじめ入った状態で開き、利用者は送る前に内容を確認でき、消すこともできる（FR-008）
- Q: 迷惑な送信（連投・無意味な内容の大量送信）への対策をこの機能で行うか？ → A: 行わない。フォームサービス側の仕組みに任せる
- Q: 導線をどういう形にし、案内をどこで見せるか？ → A: 全画面のフッターに「フィードバック」のリンクだけを置く。リンクを押すと UMIYOMI 内の案内画面が開き、案内（FR-004 の 3 点）と外部フォームを開く操作を表示する。予報画面から来たときは、フォームに入れる地点・最終更新日時も案内画面で見せる（FR-002、FR-004、FR-008、FR-013）
- Q: 案内画面と外部フォームをどう開くか？ → A: 案内画面へは同じタブで移動し、案内画面には元の画面（トップ画面または予報画面）へ戻るリンクを置く。外部フォームは新しいタブで開く（FR-003、FR-014）
- Q: 予報の取得に失敗した画面・入力を受け付けなかった画面から来たとき、フォームに何を入れるか？ → A: 取得に失敗したときは地点の緯度・経度だけを入れる（最終更新日時はない）。入力を受け付けなかったときは、利用者が入力した文字列（緯度欄・経度欄それぞれ、1 欄あたり最大 100 文字）を入れる。いずれも案内画面に表示し、フォームで消せる（FR-015）
- Q: 案内画面が受け取る値（地点・最終更新日時・入力の文字列）は誰でも作れるリンクで渡せる。どう扱うか？ → A: 決まった形の値だけを受け付ける。緯度・経度は範囲内の数値、最終更新日時は「YYYY/MM/DD HH:mm」の形、入力の文字列は先頭 100 文字までとし、利用者が入力した文字列であることが分かる引用の形で表示する。形に合わない値は表示せず、フォームにも入れない（FR-016、FR-017）
- Q: フォームを開くとき、利用者がフォームで消せない経路で地点の情報が外部サービスへ渡らないようにするか？ → A: する。フォームを開くときに、案内画面のアドレス（地点の情報を含む）を外部サービスへ伝えない（FR-018）
- Q: 外部フォームの前提条件は？ → A: アカウントやログインなしで送れること、欄にあらかじめ値を入れた状態で開けることを、フォームサービスと設定の条件とする（Assumptions）
- Q: UMIYOMI 側で確かめられない成功基準をどうするか？ → A: UMIYOMI の画面とリンクで確かめられる形に置き換える（SC-002、SC-003）

## 背景

Web MVP（001〜003）で、緯度・経度の入力、風・波・うねりの時間別表示、お気に入り地点の保存ができるようになった。しかし現在の画面には、利用者が運営者へ意見・不具合・要望を伝える手段がない。

MVP の段階では、次のことを実際の利用者から知る必要がある。

- 表示が崩れる、予報が取得できない、入力が受け付けられないといった不具合
- 「この数値も見たい」「この表記で入力したい」といった要望（MVP 後に何を作るかの判断材料）
- 予報の値が実際の海況と大きく違って見えた、といった気づき

この機能の目的は、利用者が画面から迷わず運営者へフィードバックを送れる導線を用意することである。あわせて、UMIYOMI は航海の安全を保証しないため、フィードバックの窓口が緊急時の連絡先や出航可否の相談窓口と誤解されないようにする。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - どの画面からでもフィードバックの送り先にたどり着ける (Priority: P1)

UMIYOMI を使っていて不具合や要望に気づいた利用者が、いま見ている画面（トップ画面・予報画面）から、フィードバックを送る場所へ迷わずたどり着き、内容を書いて送れる。

**Why this priority**: 導線そのものがなければ、どんな内容も運営者に届かない。この機能の価値の中心。

**Independent Test**: トップ画面と予報画面のそれぞれで、フィードバックへの導線を見つけて操作し、フィードバックを書いて送れる場所が開くことを確認すればテストできる。

**Acceptance Scenarios**:

1. **Given** トップ画面を開いている、**When** フッターの「フィードバック」を操作する、**Then** フィードバックの案内画面が開き、そこからフォームを開ける
2. **Given** 予報画面を開いている、**When** フッターの「フィードバック」を操作する、**Then** フィードバックの案内画面が開き、そこからフォームを開ける
3. **Given** スマホ幅の画面で予報画面を開いている、**When** 画面を最後までスクロールする、**Then** フィードバックへの導線が他の要素に隠れたり重なったりせず、指で操作できる大きさで表示されている
4. **Given** フィードバックを送れる場所を開いた、**When** 内容を書いて送る、**Then** 送れたことが利用者に分かる
5. **Given** 予報画面から案内画面へ移動した、**When** 案内画面の戻るリンクを操作する、**Then** 移動する前と同じ地点の予報画面が表示され、お気に入りの内容も変わっていない
6. **Given** 案内画面からフォームを開いた、**When** フォームを送らずに閉じる、**Then** 案内画面は元のタブにそのまま残っている

---

### User Story 2 - 緊急の連絡先や出航可否の相談窓口と誤解しない (Priority: P2)

フィードバックを送ろうとする利用者が、ここは不具合・要望を伝える場所であり、返信や対応の時期は約束されないこと、海上での緊急時や出航の判断には使えないことを、送る前に理解できる。

**Why this priority**: UMIYOMI は航海の安全を保証しない。海上の緊急事態や「明日出ても大丈夫か」といった相談をフィードバックに書き込み、返信を待ってしまうと、利用者の安全に関わる。P1 で導線ができても、この案内がないと危険な使われ方をしうる。

**Independent Test**: フィードバックの案内画面に、返信を約束しないこと・緊急時の連絡先ではないこと・公式の気象情報を確認することの案内があるかを確認すればテストできる。

**Acceptance Scenarios**:

1. **Given** 利用者がフッターの「フィードバック」を操作した、**When** 開いた案内画面を見る、**Then** 「返信や対応をお約束するものではありません」に相当する案内が表示されている
2. **Given** 利用者がフッターの「フィードバック」を操作した、**When** 開いた案内画面を見る、**Then** 海上での事件・事故の緊急通報は海上保安庁（118 番）へ、という案内が表示されている
3. **Given** 利用者がフッターの「フィードバック」を操作した、**When** 開いた案内画面を見る、**Then** 出航の判断には気象庁などの公式な警報・注意報も確認するよう案内されている
4. **Given** フィードバックに関するすべての文言、**When** 内容を確認する、**Then** 「安全です」「出航できます」「問題ありません」のような断定の表現を含まない

---

### User Story 3 - 予報画面からの不具合報告で、どの地点・いつの予報の話か伝わる (Priority: P3)

予報画面で「数値がおかしい」「表示が崩れる」と気づいた利用者が、地点の緯度・経度や予報の最終更新日時を自分で書き写さなくても、どの予報についての報告か運営者に伝わる。

**Why this priority**: 地点と取得日時が分からないと、運営者は不具合を再現・調査できない。ただし P1 の導線だけでも、利用者が自分で書けば伝えられるため P3 とする。

**Independent Test**: 予報画面からフィードバックへの導線を操作し、表示中の地点の緯度・経度と最終更新日時が、送る内容に含められる状態になっていることを確認すればテストできる。

**Acceptance Scenarios**:

1. **Given** 緯度 27.75・経度 129.05 の予報画面（最終更新：2026/10/05 09:00）を開いている、**When** フッターの「フィードバック」を操作し、案内画面からフォームを開く、**Then** 案内画面に「緯度 27.75・経度 129.05、最終更新 2026/10/05 09:00 がフォームに入ります」に相当する表示があり、開いたフォームにはその値があらかじめ入っている
2. **Given** 予報画面からフィードバックを送ろうとしていて、地点の情報が送る内容に含まれる状態になっている、**When** 送る前に内容を確認する、**Then** どんな地点の情報が送られるかを案内画面とフォームの両方で送る前に見ることができ、送りたくない場合は消してから送れる
3. **Given** トップ画面（予報を表示していない）からフッターの「フィードバック」を操作する、**When** 案内画面と開いたフォームを見る、**Then** 地点の情報は表示されず、フォームにも入っていない
4. **Given** 緯度 27.75・経度 129.05 の予報の取得に失敗した旨を表示している画面、**When** フッターの「フィードバック」から案内画面を開く、**Then** 案内画面とフォームには緯度 27.75・経度 129.05 だけが入り、最終更新日時は入らない
5. **Given** 緯度欄に「北緯二十七度」と入力して受け付けられなかった画面、**When** フッターの「フィードバック」から案内画面を開く、**Then** 案内画面とフォームには入力した文字列「北緯二十七度」（と経度欄の文字列）が入り、利用者はフォームで消せる

---

### Edge Cases

- フィードバックを送る場所が一時的に開けない・送れないとき：外部フォームは新しいタブで開くため、UMIYOMI の予報の閲覧には影響しない。お気に入りの内容も失われない
- 予報画面で入力欄の値を変えて未送信のまま、フッターの「フィードバック」を操作した：案内画面へは同じタブで移動するため、戻ったときに未送信の値は残らないことがある。戻った予報画面は移動前に表示していた地点のもの
- 予報の取得に失敗したことを伝える画面（外部の予報提供元の障害など）：その画面からもフィードバックへの導線にたどり着ける。フォームには緯度・経度だけを入れる（FR-015）
- 入力が受け付けられなかったとき（003 の案内メッセージが出ている画面）：その画面からもフィードバックへの導線にたどり着ける。「この表記で入力したい」という要望を集めるため、フォームには入力した文字列を入れる（FR-015）
- 受け付けなかった入力が 100 文字を超える（003 の FR-024）：先頭 100 文字だけを入れる
- 第三者が、案内画面へのリンクに任意の文章や範囲外の値を入れて利用者に開かせる：決まった形の値だけを表示・事前入力に使い、入力の文字列は引用の形で表示する（FR-016、FR-017）。形に合わない値は無視し、案内とフォームを開く操作は通常どおり表示する
- 利用者がフィードバックに個人情報（氏名・電話番号など）を書き込む：返信用の連絡先は任意であることを示し、必須にしない
- 利用者が海上から緊急の内容を書き込む：導線の近くの案内（User Story 2）で、送る前に緊急通報先を示す。UMIYOMI 側で内容を読んで緊急対応することはない
- localStorage が使えない環境：フィードバックの導線は localStorage に依存せず、同じように使える
- 同じ利用者が短時間に何度も送る・無意味な内容を大量に送る：UMIYOMI 側では対策しない。フォームサービス側の仕組みに任せる
- フォームの URL が設定されていない環境（開発環境など）：フィードバックへの導線を表示しない。予報の閲覧などほかの機能はそのまま動く
- 予報画面の緯度・経度が、フォームに入れる前の値と食い違う：フォームには予報画面で表示している地点（十進数の緯度・経度）を入れる。入力欄の未送信の値（003 の FR-021）は使わない

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: 利用者は、トップ画面と予報画面（予報の取得に失敗した旨・入力を受け付けなかった旨を表示している状態を含む）から、フィードバックを書いて送れる場所へ移動できなければならない。送り先は運営者が用意する外部のフォームサービスとし、UMIYOMI 側でフィードバックの内容を受け取ったり保存したりしてはならない
- **FR-002**: フィードバックへの導線は、全画面共通のフッターに「フィードバック」のリンクとして表示し、スマホ幅でも他の要素と重ならず、指で操作できる大きさでなければならない。リンクを押すと、外部フォームではなく UMIYOMI 内のフィードバックの案内画面を開く
- **FR-003**: フィードバックへの導線を操作しても、お気に入りの内容が失われてはならない。案内画面から元の画面へ戻ったとき、予報画面から来た場合は同じ地点の予報画面が表示されなければならない。入力欄に入力して未送信だった値は、戻ったときに残っていなくてもよい
- **FR-004**: フィードバックの案内画面には、外部フォームを開く操作より前（上）に、次の案内を表示しなければならない：(1) 返信や対応を約束しないこと、(2) 海上での事件・事故の緊急通報は海上保安庁（118 番）へ連絡すること、(3) 出航の判断には気象庁などの公式な警報・注意報も確認すること
- **FR-005**: フィードバックに関する文言（導線の表示名・案内・送信後の表示）は、航海・出航の安全を断定する表現（「安全です」「出航できます」「問題ありません」など）を含んではならない
- **FR-006**: 利用者は、フィードバックの種類（不具合・要望・予報の値についての気づき・その他）が分かるように送れなければならない
- **FR-007**: 返信用の連絡先の記入は任意でなければならない。連絡先を書かなくても送れなければならない
- **FR-008**: 予報画面からフィードバックの案内画面へ移動したとき、案内画面にはフォームに入る地点の緯度・経度と予報の最終更新日時を表示し、そこから開いたフォームには表示中の地点の緯度・経度と予報の最終更新日時（「YYYY/MM/DD HH:mm」の形）があらかじめ入った状態でなければならない。利用者は送る前にその内容を確認でき、消すこともできなければならない。トップ画面から移動したときは地点の情報を入れない
- **FR-009**: フィードバックの送り先が利用できない状態でも、予報の閲覧・入力・お気に入りの機能は影響を受けずに動かなければならない
- **FR-010**: お気に入り地点の一覧（localStorage の内容）は、フィードバックの内容として自動で送ってはならない
- **FR-011**: フィードバックの導線と案内は、localStorage が使えない環境でも同じように表示・操作できなければならない
- **FR-012**: フォームの URL が設定されていない場合、フッターの「フィードバック」のリンクを表示してはならない（リンク先のない導線を見せない）
- **FR-013**: フィードバックの案内画面は、外部フォームを開く操作を 1 つだけ持つ。案内画面では予報の取得や表示を行わず、予報を取得する回数（外部の予報提供元への問い合わせ）を増やしてはならない
- **FR-014**: 案内画面へは同じタブで移動し、案内画面には元の画面（トップ画面または予報画面。予報画面なら同じ地点）へ戻るリンクを置かなければならない。外部フォームは新しいタブで開かなければならない
- **FR-015**: 予報の取得に失敗した旨を表示している画面から案内画面へ移動したときは、地点の緯度・経度だけを案内画面に表示し、フォームに入れなければならない。入力を受け付けなかった旨を表示している画面から移動したときは、利用者が緯度欄・経度欄に入力した文字列（1 欄あたり先頭 100 文字まで）を案内画面に表示し、フォームに入れなければならない。いずれもフォームで消せなければならない
- **FR-016**: 案内画面が受け取る値は、決まった形のものだけを表示・フォームへの事前入力に使わなければならない。緯度は -90〜90、経度は -180〜180 の数値、最終更新日時は「YYYY/MM/DD HH:mm」の形、受け付けなかった入力の文字列は 1 欄あたり先頭 100 文字までとする。形に合わない値は、案内画面に表示せず、フォームにも入れてはならない（そのときも案内とフォームを開く操作は表示する）
- **FR-017**: 受け付けなかった入力の文字列は、案内画面で利用者が入力した文字列であると分かる引用の形で表示し、UMIYOMI からの案内文と区別できなければならない
- **FR-018**: 外部フォームを開くとき、案内画面のアドレス（地点の情報や入力の文字列を含む）を外部サービスへ伝えてはならない。外部サービスへ渡る地点の情報は、フォームの欄に入れた値（利用者が送る前に消せるもの）だけとする

### Key Entities *(include if feature involves data)*

- **フィードバックの案内画面**: フッターの「フィードバック」から開く UMIYOMI 内の画面。FR-004 の案内、外部フォームを開く操作、（予報画面から来たときのみ）フォームに入る地点の緯度・経度と最終更新日時を表示する。フィードバックの内容は受け取らない
- **フィードバック**: 利用者が運営者へ送る 1 件の連絡。種類（不具合・要望・予報の値についての気づき・その他）、本文、任意の返信用連絡先、（利用者が消さなかったとき）予報画面の地点の緯度・経度と予報の最終更新日時、または受け付けなかった入力の文字列を持つ。UMIYOMI の画面上に過去のフィードバックを一覧表示することはない

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 初めて使う利用者が、トップ画面・予報画面のどちらからでも、10 秒以内にフィードバックへの導線を見つけ、2 回の操作（フッターのリンク → フォームを開く操作）でフォームを開ける
- **SC-002**: トップ画面・予報画面（取得に失敗した状態・入力を受け付けなかった状態を含む）のすべてで、フッターのリンクから案内画面を経て、2 回の操作で外部フォームが開く
- **SC-003**: 予報画面から開いたフォームには、100% の場合で表示中の地点の緯度・経度と最終更新日時が入っている。形に合わない値を含むリンクから開いた場合、その値が案内画面とフォームに入る割合は 0% である
- **SC-004**: スマホ幅（幅 360px 程度）のトップ画面・予報画面で、導線が他の要素と重ならず、横スクロールなしに操作できる
- **SC-005**: フィードバックの導線と案内のすべての文言に、安全を断定する表現が 0 件である
- **SC-006**: フィードバックの送り先が利用できない状態でも、予報の表示・入力・お気に入りの保存が 100% 従来どおり行える

## Assumptions

- 対象は Web MVP の画面（トップ画面・予報画面）。Flutter アプリ内のフィードバック導線は、アプリ化のときに検討する
- フィードバックを送るのにログインやアカウント登録は不要（MVP ではアカウント機能を作らない）
- 運営者は届いたフィードバックを人が読む。自動での返信・分類・チケット管理などは範囲外
- UMIYOMI の画面上で、送ったフィードバックの履歴や運営者からの返信を表示する機能は作らない
- フィードバックの導線の表示名は日本語で、既存の画面の文言と同じ調子にする
- 不具合の調査に使う情報は、地点の緯度・経度・最終更新日時・受け付けなかった入力の文字列に限る。端末の種類・ブラウザの種類などを自動で集めることはこの機能の範囲外
- フィードバックのフォームは運営者が外部のフォームサービスで用意し、その URL を UMIYOMI に設定する。フォームには、種類（FR-006）・本文・任意の返信用連絡先（FR-007）・地点の緯度・経度・最終更新日時の欄を運営者が作る
- 外部フォームは、アカウントの作成やログインなしで送れるように設定する（UMIYOMI がログイン不要であることと揃える）。ログインを求める設定（回答者のメールアドレスの収集など）にはしない
- 外部フォームのサービスは、欄にあらかじめ値を入れた状態でフォームを開けるものを使う。この条件を満たさないサービスでは User Story 3（地点の情報の事前入力）が成り立たない
- 案内画面のアドレスには地点の情報や受け付けなかった入力の文字列が含まれ、予報画面のアドレスと同じく UMIYOMI のアクセス記録に残りうる。この機能で特別な扱いはしない
- 送信できたことの表示（User Story 1 の Acceptance Scenario 4）、届いたフィードバックの保管、迷惑な送信への対策は、フォームサービスの機能に任せる
- 届いたフィードバックの扱い（保管期間・取り扱い）についての利用者への説明は、フォーム側に運営者が記載する
